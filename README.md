# triton-cachekit

**See what is in a [Triton](https://github.com/triton-lang/triton) kernel cache, find out why a kernel
recompiled instead of hitting it, and build and ship caches so servers start warm.**

[![CI](https://github.com/cb-Sigma/triton-cachekit/actions/workflows/ci.yml/badge.svg)](https://github.com/cb-Sigma/triton-cachekit/actions/workflows/ci.yml)
[![License: Apache-2.0](https://img.shields.io/github/license/cb-Sigma/triton-cachekit)](LICENSE)
[![Python](https://img.shields.io/python/required-version-toml?tomlFilePath=https%3A%2F%2Fraw.githubusercontent.com%2Fcb-Sigma%2Ftriton-cachekit%2Fmain%2Fpyproject.toml)](pyproject.toml)

Triton JIT-compiles GPU kernels on first use and keeps the results in `TRITON_CACHE_DIR`. PyTorch
Inductor, vLLM, SGLang and many kernel libraries sit on top of it, so an inference server with a cold
cache pays the compile time at start-up, and a cache that *should* have been warm but silently missed
pays it again. `triton-cachekit` is a small, dependency-free command line tool for that cache:

| Command | What it does | Needs Triton? | Needs a GPU? |
| --- | --- | --- | --- |
| `inspect` | List entries: kernel, target, options, Triton version, stages, sizes; flag incomplete, corrupt or mis-relocated entries | no | no |
| `record` / `explain` | Log every *component* of each cache key, then compare two runs and say which component made a kernel miss, and what to do about it | `record` yes, `explain` no | no |
| `stats` | Compile time by kernel and stage, and the share a warm cache would remove | no | no |
| `prewarm` | Fill a cache for a named GPU target on a machine that has no GPU | yes | **no** |
| `verify-hit` | On the GPU host: report hit/miss per prewarmed kernel and why | yes | yes |
| `pack` / `unpack` / `relocate` | Tar or OCI-layout archive with manifest and checksums; fixes the absolute paths that stop a copied cache from being hit | no | no |
| `diff` / `prune` | Compare two caches; delete by age, size, target, state | no | no |

> **Status: alpha, and honest about it.** Everything below was run on a CPU-only machine against the
> Triton 3.8.0 and 3.9.0 wheels. **Nothing was run on a real GPU.** In particular, that a cache built
> by `prewarm` is hit on a real GPU host is *not verified*; see
> [What is and is not proven](#what-is-and-is-not-proven). This is an independent project, not
> affiliated with or endorsed by the Triton maintainers, OpenAI, AMD or NVIDIA.

## Install

```console
$ pip install git+https://github.com/cb-Sigma/triton-cachekit
```

Python 3.11+. No dependencies. Triton itself is only needed by `record`, `prewarm`, `verify-hit`,
`fingerprint` and the `--demo` flags; install the tool into the same environment as your Triton for
those. `inspect`, `explain`, `stats`, `pack`, `unpack`, `relocate`, `diff` and `prune` work anywhere,
for example on a cache directory copied off a server.

## Why

**Start-up compile time.** Every specialisation of every kernel (each dtype combination, each
constexpr value, each autotune candidate) is a separate compilation through MLIR, LLVM and
`ptxas`. A cache makes that a one-off, provided the next process computes the same keys.

**Cache keys are full of surprises.** These are open or recently closed upstream issues, each checked
against the issue text when this README was written:

| Issue | What it says |
| --- | --- |
| [#12429](https://github.com/triton-lang/triton/issues/12429) | The on-disk key leaves out information that changes the kernel, so different kernels get the same key and load the same binary. `explain --collisions` detects this from recordings; the test suite reproduces one case on 3.8.0 and 3.9.0. |
| [#12367](https://github.com/triton-lang/triton/issues/12367) | Since PR #11832 (on `main`, not in 3.9.0) the source file path is part of the key: the same kernel at a different path never hits. |
| [#11817](https://github.com/triton-lang/triton/issues/11817) | Source location is treated inconsistently: the line number is hashed even with `TRITON_DISABLE_LINE_INFO=1`; an unset variable and `=0` hash differently. |
| [#11999](https://github.com/triton-lang/triton/issues/11999) (closed, fixed on `main`) | A copied cache directory misses once the original is gone, because group files store absolute paths. Still the behaviour of the 3.8.0 and 3.9.0 wheels; `relocate`/`unpack` work around it. |
| [#12239](https://github.com/triton-lang/triton/issues/12239) | Constexprs that compare equal but differ in type (`1` vs `1.0`) reuse each other's binary (in-process cache). |
| [#11512](https://github.com/triton-lang/triton/issues/11512), [#2688](https://github.com/triton-lang/triton/issues/2688) | Concurrent compilation into a shared cache directory on a network filesystem crashes. Prebuilt, read-mostly caches avoid the race. |
| [#11778](https://github.com/triton-lang/triton/issues/11778) | The cache uses many files per kernel and can exhaust inode quotas. `inspect` and `prune` show and bound it. |
| [#9368](https://github.com/triton-lang/triton/issues/9368), [#12222](https://github.com/triton-lang/triton/issues/12222), [#12582](https://github.com/triton-lang/triton/issues/12582) | Autotuner cache: location, mixed-architecture memoisation, colliding tuning keys. (Out of scope for now; `inspect` only lists autotune entries.) |
| [#935](https://github.com/triton-lang/triton/issues/935) | The long-running request for ahead-of-time compilation. |

When a kernel misses, Triton does not tell you why: the key is a SHA-256 of a long string, and the
cache entry does not record what went into it. `record` + `explain` make that visible.

## How Triton's cache key is built

Verified by reading the source of the **3.9.0 wheel** (and 3.8.0, and `main` at commit `8a439de` for
the differences noted). Full walk-through with line references: [docs/cache-key.md](docs/cache-key.md).

```text
key string = triton_key()                    python/triton/runtime/cache.py  triton_key()
           - src.hash()                      python/triton/compiler/compiler.py  ASTSource.hash()
           - backend.hash()                  python/triton/backends/{nvidia,amd}/compiler.py
           - backend_options.hash()          same files, CUDAOptions.hash() / HIPOptions.hash()
           - str(sorted(env_vars.items()))   _C/libtriton get_cache_invalidating_env_vars()
                                             assembled in runtime/cache.py get_cache_key()
directory  = base32(sha256(key string)) without padding      compiler.py compile(), cache.py _base32()
```

| Component | What goes in | Consequence |
| --- | --- | --- |
| `triton_key()` | Triton version + SHA-256 of `runtime/cache.py`, every module under `compiler/`, `backends/`, `language/`, and the `libtriton` shared library | Only a byte-identical Triton install can hit. Different version, different Python minor version (different wheel), or a locally patched file: every key changes. |
| `src.hash()` | The kernel's function hash, the specialisation attributes, the argument types, the constexpr values | See the next rows. |
| function hash (`JITCallable.cache_key`) | Source text from `def` on; the hash of every `@triton.jit` function it calls (plus its `noinline` flag); global `tl.constexpr` values read by name; and the **start line number** (3.8.0, 3.9.0) or **file path, start line, `def` line and column** (`main` after PR #11832) | Editing a helper changes every caller. Adding a comment *above* a kernel changes its key. On `main`, installing the package at another path changes every key. |
| specialisation | Per argument: pointer dtype; `i32`/`i64`; an integer equal to 1 becomes a constexpr; pointers and integers divisible by 16 get `tt.divisibility=16` | The same kernel called with an unaligned view, or with `n=1000` instead of `n=1024`, is a different key. |
| `backend.hash()` | CUDA: the output of `ptxas --version` + compute capability. AMD: target + AMD code generator revision | One cache per GPU architecture; `TRITON_PTXAS_PATH` changes it. |
| `backend_options.hash()` | Every option field (`num_warps`, `num_stages`, `enable_fp_fusion`, `debug`, `arch`, ...); extern libraries by *content* | Some defaults come from the environment when options are built (`TRITON_DEFAULT_FP_FUSION`, `TRITON_DEBUG`, `PTXAS_OPTIONS`, `TRITON_OVERRIDE_ARCH`, `TRITON_LIBDEVICE_PATH`). |
| env vars | Every *set* variable in `CACHE_INVALIDATING_ENV_VARS` (`include/triton/Tools/Sys/GetEnv.h`), booleans normalised to `true`/`false` | Unset and explicitly-set-to-default are different keys. |

Separately from the key, an entry is only *loaded* if `__grp__<kernel>.json` exists and every file it
lists exists. In 3.8.0 and 3.9.0 that file lists **absolute paths**, so a cache directory mounted or
copied to a new path misses for every entry (`inspect` reports this as `stale-paths`).

## Commands

### `inspect`

```console
$ triton-cachekit inspect                      # $TRITON_CACHE_DIR or ~/.triton/cache
$ triton-cachekit inspect /mnt/cache --format json
$ triton-cachekit inspect ./cache --target cuda:90 --kernel '*attention*' --locations
$ triton-cachekit inspect ./cache --problems --strict     # exit 1 if any entry is unloadable
```

Reads the directory layout directly; Triton is not imported. Entry states: `ok`, `stale-paths`
(group file points at another directory: needs `relocate`), `incomplete` (missing group file, binary
or metadata, typically an interrupted compilation) and `corrupt` (unparsable JSON, hash mismatch).
The kernel's source file and line are recovered from MLIR debug locations when present. Autotuner
results and compiled launcher stubs that live in the same directory are listed separately.

Layouts verified: entries written by the **3.8.0 and 3.9.0** wheels (real entries, in the test
suite), and the relative-path group format of `main` (from source, with synthetic entries).

### `record` and `explain`

```console
$ triton-cachekit record -o build.jsonl  -- python warmup.py        # on the build machine
$ triton-cachekit record -o server.jsonl -- vllm serve ...          # on the server
$ triton-cachekit explain build.jsonl server.jsonl
$ triton-cachekit explain --collisions run1.jsonl run2.jsonl        # different kernels, same key
```

`record` runs any command with the recorder switched on in every Python process that imports
Triton. Alternatively put `import triton_cachekit.record` at the top of your program and set
`TRITON_CACHEKIT_RECORD=/path/run.jsonl`. `--no-source` (or `TRITON_CACHEKIT_RECORD_SOURCE=0`)
keeps kernel source text out of the file; you then get "source differs" without the diff.

The recorder does **not** re-implement the key. It wraps Triton's own `get_cache_key()` and writes
down each argument's contribution next to the finished key, wraps `JITCallable.cache_key` and
`DependenciesFinder._update_hash` to learn which callees feed a kernel's hash, and uses Triton's
`knobs.compilation.listener` for hit/miss and stage timings. Format:
[docs/recording-format.md](docs/recording-format.md).

`explain A B` goes through every compilation in B and reports, for each miss, the closest
compilation in A and the components that differ, root cause first: `triton.version`, `triton.files`
(which files), `backend.target`, `backend.toolchain`, `env`, `options`, `source.text` (with a diff),
`source.location.line`, `source.location.file`, `source.dependency.*` (which callee, and why),
`source.globals`, `specialization.signature`, `specialization.constants`, `specialization.attrs`.
If B's key equals A's but B still missed, it says so and points at the cache contents instead.
`--format json` for machines, `--fail-on-miss` for CI.

### `stats`

```console
$ triton-cachekit stats server.jsonl
```

From a recording: total time inside `triton.compile`, split into misses and hits, per kernel and
per stage. "A warm cache would remove" charges the median measured cost of a hit for every miss
(a hit is not free); with no hits in the recording the figure is labelled an upper bound.

### `prewarm`

```console
$ triton-cachekit prewarm --manifest prewarm.toml --cache-dir ./cache            # from a manifest
$ triton-cachekit prewarm --from-recording server.jsonl --cache-dir ./cache      # replay a real run
```

Compiles the listed kernels for a named target (`cuda:80`, `cuda:90`, `hip:gfx942:64`, ...) on a
machine without that GPU. It installs a stand-in driver that reports the target, then calls
Triton's own `kernel.warmup(...)` (manifest) or `kernel.preload(...)` (recording), so the keys and
artifacts are produced by Triton's normal JIT path. Each kernel runs in its own subprocess with a
timeout (`--timeout`, `-j` for parallelism). It writes a manifest of every entry produced and a key
recording of the run. Manifest format and a full example: [docs/prewarm.md](docs/prewarm.md),
[examples/](examples/).

Before compiling you can check everything that *can* be checked without the GPU:

```console
server$ triton-cachekit fingerprint -o server.json       # Triton files, key-relevant environment
build$  triton-cachekit prewarm --manifest prewarm.toml --cache-dir ./cache \
            --server-fingerprint server.json             # refuses to build a cache that cannot hit
```

**`prewarm` output is not verified on real GPUs.** The command prints this, lists the reasons a
hit could fail, and sets `"verified_on_real_gpu": false` in its manifest.

### `verify-hit`

```console
gpu-host$ triton-cachekit unpack cache.tar.gz "$TRITON_CACHE_DIR"
gpu-host$ triton-cachekit verify-hit --manifest prewarm-manifest.json --prewarm-recording prewarm.rec
```

Re-runs the manifest's specialisations through the **real** driver in warm-up mode (nothing is
launched on the GPU), and reports per kernel: `HIT`, or `MISS` with the reason: a different key
(with the full `explain` breakdown against the prewarm recording) or the same key but no loadable
entry. Exit status 0 only if everything hit. Misses are compiled and stored, as the application
would. Without a GPU it stops with an error rather than claiming anything; `--fake-driver` exists
to test the tool itself and labels its output `SIMULATION`.

The strongest check is still your real application: `triton-cachekit record -- <your server>` on
the GPU host, then `triton-cachekit explain prewarm.rec server.jsonl`.

### `pack`, `unpack`, `relocate`

```console
$ triton-cachekit pack ./cache -o cache.tar.gz               # or cache.tar, or a directory = OCI layout
$ triton-cachekit unpack cache.tar.gz /var/cache/triton      # verifies checksums, fixes paths
$ triton-cachekit relocate /var/cache/triton                 # after docker COPY, rsync, a new mount point
```

The archive carries a manifest with a SHA-256 per file, the Triton version and target of every
entry and (when Triton is installed where you pack) a fingerprint of that install. `unpack`
verifies every checksum, refuses path traversal, and rewrites the absolute paths in group files
for the destination. It warns when the Triton installed at the destination cannot hit the entries.
`--format oci` writes an [OCI image layout](https://github.com/opencontainers/image-spec/blob/main/image-layout.md)
with a single gzip layer, pushable with tools such as `skopeo copy oci:DIR docker://...` or `oras`
(layout checked structurally in the tests; pushing to a registry was not tested). Format:
[docs/archive-format.md](docs/archive-format.md).

*Relocatable?* The files are, once group files are rewritten. Whether the entries are *hit*
elsewhere is decided by the key: same Triton build, same environment variables, same source at the
same line, and on `main` the same source path. `pack` prints this and records it in the manifest.

### `diff` and `prune`

```console
$ triton-cachekit diff ./cache-a ./cache-b
$ triton-cachekit prune ./cache --older-than 30d --max-size 2G           # dry run
$ triton-cachekit prune ./cache --incomplete --not-triton-version 3.9.0 --yes
```

`diff` lists entries on one side only, entries with the same key but different content, and what
the stored metadata can say about same-named entries with different keys (often nothing: the cache
does not store what was hashed, which is what `record`/`explain` are for). `prune` never deletes
without `--yes`. Triton does not touch timestamps on a hit, so "older" means "compiled longer ago".

## What is and is not proven

| Claim | Status |
| --- | --- |
| `inspect` parses real entries written by Triton 3.8.0 and 3.9.0 (CUDA and AMD targets), and detects missing group files, missing binaries, truncated metadata, stale paths | **Tested** against entries produced by those wheels |
| The recorder captures each key component and its recorded hash equals the directory Triton writes | **Tested** on 3.8.0 and 3.9.0 |
| `explain` names the right component when exactly one thing changes: kernel source, a called function, a constexpr global, line shift, file move, env var, option, target, constexpr value, dtype, pointer alignment | **Tested** with real compilations on 3.8.0 and 3.9.0 |
| A cache directory moved to another path misses on 3.8.0/3.9.0 and hits again after `relocate` / `unpack` | **Tested** (CPU, fake driver) |
| `prewarm` writes complete entries (including `.cubin` / `.hsaco`) without a GPU, and a second process on the same machine hits them | **Tested** |
| Replaying a recording with `prewarm --from-recording` reproduces exactly the keys of the recorded run | **Tested** (the recorded run itself used the fake driver) |
| **A prewarmed cache is hit by a process using a real GPU driver** | **Not verified.** No GPU was available. |
| Binaries produced by cross-compiling are correct and run on the target GPU | **Not verified.** They come from Triton's own pipeline for that target, but none was executed. |
| The source-path component on Triton `main` (PR #11832) and the relative group format | Read in source and unit-tested with synthetic data; **not run** against a `main` build |
| Real-world caches from vLLM / PyTorch Inductor / SGLang | **Not tested.** Only this project's own small kernels were compiled. |
| Windows, macOS | **Not tested** (Linux only) |

**How to verify the open claim yourself** (10 minutes on any machine with a supported GPU):

```console
build$ triton-cachekit prewarm --manifest examples/prewarm.toml --target cuda:<capability> --cache-dir ./cache
build$ triton-cachekit pack ./cache -o cache.tar.gz
gpu$   examples/verify_on_gpu.sh cache.tar.gz prewarm-manifest.json prewarm-manifest.rec
```

Both sides need the same Triton wheel and Python version; `<capability>` is
`torch.cuda.get_device_capability()` as two digits (8.0 becomes `80`). Whatever the outcome, please
[open an issue](https://github.com/cb-Sigma/triton-cachekit/issues/new/choose) with the output; a
miss comes with the component that differed, which is exactly the information needed to fix it.

Why a real host might still miss, as far as the source shows: the real driver reporting a different
target than you named; integer arguments or tensor alignment differing from the manifest (prefer
`--from-recording`); a different `ptxas` (`TRITON_PTXAS_PATH`); environment variables; a Triton
install that is not byte-identical.

## Supported Triton versions and failure behaviour

| Triton | `inspect` / `pack` / ... | `record` / `prewarm` / `verify-hit` |
| --- | --- | --- |
| 3.8.0 | tested | tested (full test suite) |
| 3.9.0 | tested | tested (full test suite) |
| `main` @ 8a439de | layout read from source | hooks match by inspection; not run |
| others | best effort: unknown metadata fields are shown, unknown layouts reported | checked at start-up, see below |

This tool depends on Triton internals that are not a public API and do change (the key gained the
source path between 3.9.0 and `main`, the group file changed encoding). It is written to notice:

* The recorder checks the shape of every function it hooks (`get_cache_key`'s parameters,
  `JITFunction._do_compile`, `DependenciesFinder._update_hash`, the listener knob, ...) before
  installing. On a mismatch it raises `UnsupportedTritonError` listing each difference and records
  **nothing**, rather than producing a recording that looks plausible and is wrong.
* While recording, if Triton reports a compilation whose hash does not correspond to a key the
  recorder saw, a warning is raised and written into the recording.
* Per-file Triton hashes are only trusted when re-joining them reproduces Triton's own
  `triton_key()`; otherwise only the digest is compared.
* Which location fields are hashed is detected from the installed Triton and stored in the
  recording, so `explain` does not apply 3.9.0 rules to a newer build.
* `inspect` never needs Triton and tolerates missing metadata fields.

## Related work

* **[redhat-et/GKM](https://github.com/redhat-et/GKM)** (GPU Kernel Manager) and its **MCV** tool
  package a kernel cache *captured on a real GPU node* into a signed OCI image and distribute it
  across a Kubernetes cluster with an operator, including preflight checks that the node's GPU
  matches. If you run Kubernetes and already have a warm cache, that is the more complete
  distribution story (signing, operator, PVCs). It does not explain cache misses or build caches
  without a GPU.
* **[redhat-et/MCU](https://github.com/redhat-et/MCU)** (MCM, Model Cache Manager) indexes Triton
  and vLLM caches into a database, searches and prunes them, tracks hits at runtime, and warms vLLM
  caches by running vLLM in GPU containers. Overlaps with `inspect`/`prune` here; triton-cachekit
  adds key-level explanations, GPU-less prewarming and relocation, and needs no database.
* **Triton's own AOT path** ([`python/triton/tools/compile.py`](https://github.com/triton-lang/triton/blob/main/python/triton/tools/compile.py))
  compiles one kernel into C source embedding the binary, for launching *without* Python. It
  bypasses the JIT cache rather than filling it. Triton also has an internal compile-warm-up
  harness for its CI (`python/triton/_compile_warmup*.py`), which is not a public tool.
* **[meta-recsys/triton-aot](https://github.com/meta-recsys/triton-aot)**: an AOT compilation
  library for inference serving (a single initial commit when checked).
* **[ROCm/aotriton](https://github.com/ROCm/aotriton)**: ahead-of-time compiled Triton math library
  for AMD GPUs; ships prebuilt kernels rather than managing the JIT cache.
* **PyTorch compile caches** (`torch.compiler.save_cache_artifacts` / "mega-cache") bundle
  Inductor's artifacts for `torch.compile` users and should be preferred when your kernels come
  from Inductor. They operate above Triton and are captured on the target GPU.

If one of these descriptions is inaccurate, please open an issue.

## FAQ

**Is prewarming on a CPU machine "real"?** The compilation is: Triton's code generators and the
bundled `ptxas` run on the CPU, and the resulting directory is indistinguishable in layout from
one written on a GPU host. Whether the GPU host asks for the same key is the unverified part.

**Can I share one cache between Triton versions or Python versions?** You can store them together
(keys never collide across builds), but an entry is only ever hit by the exact build that wrote
it. `inspect` shows the version per entry; `prune --not-triton-version` cleans up.

**My container mounts the cache read-only at a different path and everything recompiles.** On
3.8.0/3.9.0 that is the absolute-path group file. Run `triton-cachekit relocate DIR` in the image
build, at the final path, or build the cache at the path it will be mounted at.

**Does the recorder slow my application down?** It adds work only when Triton compiles or loads a
kernel (hashing the entry's files, one JSON line). It does nothing on the kernel launch path.

**Does it send data anywhere?** No. No network access, no telemetry. Recordings contain file paths,
environment variable values for `TRITON_*` and, unless disabled, kernel source text: review before
sharing.

**Does it support the Redis remote cache?** Not directly. Triton's `RemoteCacheManager` uses the
same keys and materialises entries into the local cache directory, which `inspect` can read;
`record`/`explain` work unchanged because the key is computed the same way.

**Autotuning?** `prewarm` compiles every configuration of an autotuned kernel (via
`Autotuner.warmup`), but choosing the best one needs timing on a GPU, which is out of scope.
